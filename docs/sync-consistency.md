# 云端同步一致性

基于 PR #7（`fix/data-reliability`，`c4c9de7`）。本批是独立的后续 PR，必须先合入 #7，再把本 PR 的目标分支改为 main。没有部署线上 Worker，也没有向真实家庭写入测试数据。

## 已复现的问题

旧 Worker 将整个家庭快照存入 Workers KV。两个设备读到相同快照后，各自添加指令再上传，最后一次写入覆盖前一次。用原 Worker 和隔离 KV 测试：两次携带同一 `If-Match` 的写入都返回 200，最终只有后一笔指令；客户端传入的未来 `_syncTs` 也被直接接受。客户端的“先 GET 再 POST”和页面内互斥锁不能解决服务端竞态。

本批把服务端存储、主程序合并、家长端重试和推送读取一起切换，避免只修改某一端后仍有旧路径覆盖数据。

## 协议与数据约定

- 每个同步码对应一个 SQLite-backed Durable Object。当前快照、前一版备份、递增 revision 和请求回执在同一个存储事务中提交。
- `GET /?code=…` 返回原有字符串值快照，并附 `X-Sync-Protocol: 2`、`X-Sync-Revision` 和 `ETag`。不存在的家庭返回 404、revision 0。
- `GET /ts?code=…` 只读取版本头，返回 `{ts, revision, protocol: 2}`；不读取大快照。
- POST 必须包含 `If-Match: "当前revision"` 和 `Idempotency-Key`。过期版本返回 409 `REVISION_CONFLICT`；缺少条件返回 428 `UPGRADE_REQUIRED`。
- 相同请求编号、原始字节和基准版本重试，返回原回执而不再写入；编号与内容不匹配返回 409。保留最近 128 个请求回执；更老请求仍受 revision 检查保护，不能把旧快照重新写入。家长指令还有稳定业务 ID，跨刷新重放时可识别已接受甚至已执行的指令。
- revision 决定并发先后；`_syncTs` 由服务器生成，设备时钟不能决定胜负。旧客户端时间戳只用于前端先发布期间的旧协议兼容。
- 业务值仍是 `app_*` 字符串。排除本机同步码、同步显示时间和测试模式开关。校验对象结构、成员格式、键名、版本表和 8 MiB 请求上限。成员意外清空/默认测试员覆盖真实家庭受到保护。
- 大快照按 UTF-8 字节分为 64 KiB 块，避免单值限制；在事务内整体提交。保留当前和前一版，失败请求不旋转备份。

## 主程序与家长端

主程序保存最近确认的云端快照及 revision，使用“共同基准 / 当前本机 / 当前云端”三方合并。不同字段、不同记录的修改合并；同一字段冲突、删除与编辑冲突、无法识别身份的数组冲突，暂停自动上传并保留双方内容。用户选择只作用于冲突部分，其他修改继续合并。确认前重新读取版本；如果双方又发生变化，必须重新核对，旧选择不能直接覆盖新内容。

账务收据和托管记录沿用已有的确定性合并与账本投影。上传响应只更新已确认基准，不替换等待响应期间新发生的本机编辑。恢复备份或切换家庭后，旧请求不能应用到新上下文。首次使用页同样记录新协议基准。

`_sync_checkpoint_v2` 不参与家庭同步或普通业务备份，仅保存在 IndexedDB；不重复写进容量较小的同步退出日志。IndexedDB 降级时只在内存保留基准，退出后通过保守合并恢复，必要时提示冲突。不能因为丢失基准而采用设备时间戳覆盖云端。

家长端只提交操作涉及的键，基准来自用户实际看到的数据；收到 409 后重新读、合并、再条件写入。提交前将待确认操作保存在本机，网络错误保留原指令 ID；刷新或重新连接后继续确认。已有操作未确认时，不把再次点击静默当成另一笔扣款。历史数量上限不删除 pending 指令，避免孩子离线时积压的操作被新指令挤掉；新指令和家长留言使用随机唯一 ID。绑定、解绑也必须得到云端成功回执才能显示完成。

冲突面板可下载双方的诊断备份。文件 `daka-sync-conflict-backup.json` 包含 `local`、`cloud` 两个独立的备份 2.0 对象；它是复核用组合文件，不能把整个组合文件直接导入。需要恢复时先提取其中一侧，走现有备份导入校验。密码、API key、配对信息不在冲突面板直接展示；导出的原始备份仍需妥善保存。

推送 Worker 使用 `SYNC_SERVICE` 服务绑定读取权威快照，服务报错时停止该次读取，不能回退到迁移前的旧 KV。

## 分阶段发布

这是待评审实现；合并前端不会自动完成 Worker 迁移。发布前先在独立 Worker、独立 KV 和测试家庭演练，确认当前 Cloudflare 账户支持 SQLite Durable Objects，保留前端、Worker 和 KV 的可恢复版本。

1. **先发布兼容前端**：新前端可读取旧协议；此时旧 Worker 的并发覆盖风险仍存在，不能宣称已经启用事务同步。让主程序、家长端刷新到新版本。
2. **备份并冻结旧写入**：导出家庭数据和 KV 当前/备份快照，记录成员、任务、指令和账务数量。部署本 PR 的同步 Worker，保持 `wrangler.toml` 中 `SYNC_MODE="readonly"`。此模式只读旧 KV，POST 返回 503；客户端保留修改。不要同时运行另一条绕过入口写旧 KV 的路径。
3. **核对迁移基准**：等待旧写入传播，比较已导出的最新有效快照、KV 和只读端返回内容。KV 存在最终一致性，不能只等待一个固定秒数就认为校验完成；发现差异继续保持只读，先确认哪份是最新业务数据。
4. **切换推送读取**：部署 `push-wrangler.toml` 的 `SYNC_SERVICE` 绑定。验证推送读取走同步 Worker；此时同步 Worker 仍只读 KV。
5. **激活事务服务**：核对上述基准后，将部署使用的 `SYNC_MODE` 改为 `active`。每个家庭第一次访问时只导入一次旧 KV（及有效旧备份）；导入成功后的权威数据是 Durable Object。旧 KV 保留但不再更新。旧客户端写入收到 428，必须刷新；不要为旧客户端重开无条件写入。
6. **发布后验收**：测试家庭验证同时提交、两端编辑、响应丢失、刷新重连、冲突处理、正确金额及逐条通知；核对新 revision、当前/备份快照和推送读取。没有确认这些结果前，不扩大迁移使用范围。

本仓库默认保持 readonly，避免一次普通部署直接激活迁移。实际启用后须将所用发布配置的 mode 固定为 active；后续部署不能意外恢复默认 readonly。

## 回退边界

- **激活前**：仍以旧 KV 为基准，可保持 readonly，修复或回退兼容前端，待问题解决再启动迁移。
- **激活后**：设置 `SYNC_MODE="paused"` 暂停 POST，GET 继续读 Durable Object。不要改回 readonly，不要直接部署旧 KV 写入 Worker；这会让用户读到迁移前的旧数据。
- 需要恢复旧后端时，先 paused，逐家庭导出并核对 Durable Object 当前及备份快照，完成明确的数据迁移方案后再切换；本批不提供一键降级脚本。不要删除 Durable Object migration/namespace 来“回滚”。
- 旧前端在新服务上会被禁止写入，安全处理方式是恢复兼容前端版本。不要用放开无条件 POST 来解决。

- `npm test`：纯函数三方合并、传输重试、协调器并发、储存日志和推送读取；Miniflare 使用真实 workerd 与 SQLite Durable Object 运行服务端测试，覆盖并发 CAS、丢失回执、编号碰撞、时钟、迁移、大中文快照、备份、保护性暂停以及进程重启后的持久化。
- `npm run test:e2e`：Chromium 和 WebKit 真实页面连接隔离的 Miniflare 服务。两台家长页面同时扣款、孩子逐条查看并刷新、家长端丢失响应后刷新重连、两台主程序同字段冲突及重新确认；同时运行已有账务、能耗档位、安全区、动画与备份恢复回归。
- `npm run build`、`git diff --check`。
- 自动化不会测量真实 iPad 的功耗或温度，也不会向真实家庭服务提交数据。

## 留待后续批次

同步码仍是现有的家庭数据访问凭据，本批**没有**建立服务端家长身份认证或按角色授权。密码、API key 等敏感配置的存放与返回范围、设备配对及撤销、兑换查询/取消/核销权限，需要另一个贯穿服务端和客户端的完整批次。条件写入和去重不能替代身份校验。

本批也不是完整业务事件账本：未知数组/同字段业务冲突采取保留并提示，不做任意加总；红包、奖励转盘等其他模块的专用跨设备业务去重仍需独立审计。没有改变视觉档位、动画频率、3D 展厅或奖励规则。
